## Partie B – Écrire les enregistrements dans un serveur DNS (≈ 50 min)

### B1 – Installer BIND et déclarer une zone

```bash
sudo apt install -y bind9 bind9-dnsutils
```

Crée la **zone** (le fichier qui décrit le domaine) : `sudo nano /etc/bind/db.lab.local`

```text
$TTL 300
@   IN SOA ns1.lab.local. admin.lab.local. ( 2026101901 3600 600 86400 300 )
    IN NS  ns1.lab.local.
    IN MX  10 mail.lab.local.
    IN TXT "v=spf1 ip4:192.0.2.25 -all"
ns1  IN A 127.0.0.1
mail IN A 192.0.2.25
www  IN A 192.0.2.80
_dmarc IN TXT "v=DMARC1; p=quarantine; rua=mailto:dmarc@lab.local"
sel1._domainkey IN TXT "v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEAlabkeyfictive"
```

Puis déclare-la dans `/etc/bind/named.conf.local` (ajoute à la fin) :

```text
zone "lab.local" {
    type primary;
    file "/etc/bind/db.lab.local";
};
```

Vérifie, puis recharge :

```bash
sudo named-checkzone lab.local /etc/bind/db.lab.local
sudo named-checkconf && echo "configuration valide"
sudo systemctl restart bind9
```

## Partie E – DNSSEC : signer, valider, détecter (≈ 40 min)

### E1 – Créer les clés et signer la zone

```bash
cd /etc/bind
sudo cp db.lab.local db.lab.local.src
sudo dnssec-keygen -a ECDSAP256SHA256 -f KSK -n ZONE lab.local
sudo dnssec-keygen -a ECDSAP256SHA256 -n ZONE lab.local
for k in Klab.local*.key; do echo "\$INCLUDE $k"; done | sudo tee -a db.lab.local.src
sudo dnssec-signzone -N INCREMENT -o lab.local -f db.lab.local.signed db.lab.local.src
```

**Je comprends.** Deux clés sont créées : une **KSK** (signe les clés) et une **ZSK** (signe la zone). La commande de signature produit le fichier `db.lab.local.signed` et un fichier `dsset-lab.local.` qui contient l'**enregistrement DS**, à publier dans la **zone parente** : c'est ce qui crée la chaîne de confiance.

### E2 – Servir la zone signée

Dans `/etc/bind/named.conf.local`, remplace `db.lab.local` par `db.lab.local.signed` dans la ligne `file`, puis :

```bash
sudo named-checkconf && sudo rndc reload
dig @127.0.0.1 www.lab.local A +dnssec +noall +answer
```

**J'anticipe.** Que voit-on en plus de l'enregistrement `A` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Un enregistrement **RRSIG** : la **signature** de l'enregistrement `A`.

</details>

### E3 – Valider comme le ferait un résolveur

Crée un fichier de **confiance** à partir de l'enregistrement DS (ici, le domaine de laboratoire n'a pas de parent : c'est **toi** qui joues la racine de confiance), puis interroge avec `delv`, un outil qui **valide** :

```bash
cd /etc/bind
awk '{ d=""; for(i=7;i<=NF;i++) d=d $i; printf "trust-anchors {\n  \"lab.local.\" static-ds %s %s %s \"%s\";\n};\n", $4,$5,$6,d }' dsset-lab.local. | sudo tee /root/ta.conf
sudo delv @127.0.0.1 -a /root/ta.conf +root=lab.local www.lab.local A
```

### E4 – Une falsification

Simule un **attaquant qui modifie un enregistrement** : change l'adresse de `www` dans le **fichier signé**, sans re-signer :

```bash
sudo sed -i 's/192.0.2.80/192.0.2.66/' /etc/bind/db.lab.local.signed
sudo rndc reload
dig @127.0.0.1 www.lab.local A +short
sudo delv @127.0.0.1 -a /root/ta.conf +root=lab.local www.lab.local A
```

**J'anticipe.** Que renvoient `dig` et `delv` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`dig` **renvoie la fausse adresse** (`192.0.2.66`) : un client **qui ne valide pas** ne voit rien. `delv` **refuse** : « no valid signature found » / « RRSIG failed to verify ». C'est l'intérêt de DNSSEC : un résolveur qui valide **détecte** la falsification. La signature de `www` ne correspond plus aux données.

</details>

Remets la bonne adresse (`sudo sed -i 's/192.0.2.66/192.0.2.80/' /etc/bind/db.lab.local.signed`), recharge, et vérifie que `delv` redonne `fully validated`.
