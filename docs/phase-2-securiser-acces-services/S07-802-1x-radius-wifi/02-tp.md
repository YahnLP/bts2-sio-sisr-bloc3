## Contraintes

- Une machine virtuelle **Debian** avec un compte `sudo`, **instantané** avant de commencer.

- Tout reste dans la machine : le réseau de la salle n'est pas touché.

## Partie B – Installer et configurer (≈ 40 min)

### B1 – Installation et arrêt du service

```bash
sudo apt update
sudo apt install -y freeradius freeradius-utils
sudo systemctl stop freeradius
```

**Je comprends.** On **arrête le service** pour le relancer **au premier plan en mode « debug »** : chaque requête s'affiche à l'écran, ce qui est la meilleure façon de comprendre (et de dépanner) un serveur RADIUS.

### B2 – Déclarer l'authentificateur et son secret

Le fichier des clients RADIUS est `/etc/freeradius/3.0/clients.conf`. Un « client » est un **authentificateur** (borne, switch), pas un utilisateur. Le bloc `client localhost` représente l'authentificateur de **cette machine**. Modifie son **secret** :

```bash
sudo nano /etc/freeradius/3.0/clients.conf
```

Dans le bloc `client localhost { … }`, remplace la ligne `secret = testing123` par :

```text
secret = Secret-Borne-Lab
```

**Je comprends.** Le secret par défaut `testing123` est **connu de tous** : le garder en production serait une faute. Un bon secret est **long, aléatoire**, et **différent pour chaque authentificateur**.

### B3 – Déclarer les utilisateurs

Ajoute **à la fin** du fichier `/etc/freeradius/3.0/users` :

```text
alice  Cleartext-Password := "Lab-2026"
       Tunnel-Type = VLAN,
       Tunnel-Medium-Type = IEEE-802,
       Tunnel-Private-Group-Id = "20"
bob    Cleartext-Password := "Lab-2026"
```

**Je comprends.** `alice` recevra, avec l'acceptation, l'ordre d'aller dans le **VLAN 20** ; `bob` sera accepté sans VLAN. (Un fichier `users` avec des mots de passe en clair est un **outil de laboratoire** : en production, FreeRADIUS interroge l'annuaire.)

### B4 – Lancer en mode debug

Dans **un premier terminal**, lance le serveur au premier plan et **laisse-le tourner** :

```bash
sudo freeradius -X
```

Il se termine par la ligne `Ready to process requests`. Si une erreur s'affiche avant (par exemple une écoute IPv6 qui échoue), note-la : ______________________

**Point de contrôle :** capture de la ligne `Ready to process requests`.

### C4 – Un mauvais secret partagé

**J'anticipe.** Que se passe-t-il si l'authentificateur utilise un **autre secret** que celui du serveur ? ______________________

```bash
timeout 20 radtest alice Lab-2026 127.0.0.1 0 testing123
```

<details markdown="1">
<summary>Éléments de réponse</summary>

**Aucune réponse** : le serveur **ne répond pas** aux requêtes dont le secret ne correspond pas (la commande attend puis abandonne). Dans le journal du serveur, un message signale que la requête est rejetée à cause d'un secret incorrect ou d'un message invalide. C'est une **protection** : un appareil qui ne connaît pas le secret n'obtient même pas de refus.

</details>

## Partie D – PEAP et le certificat du serveur (≈ 50 min)

### D1 – Une authentification PEAP complète

`eapol_test` joue le rôle d'un client 802.1X. Crée le fichier de profil `peap.conf` :

```text
network={
  ssid="LAB"
  key_mgmt=WPA-EAP
  eap=PEAP
  identity="alice"
  password="Lab-2026"
  phase2="auth=MSCHAPV2"
}
```

Lance le test :

```bash
eapol_test -c peap.conf -a 127.0.0.1 -p 1812 -s Secret-Borne-Lab
```

**J'anticipe.** Que doit afficher la dernière ligne ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

`SUCCESS`. Dans le journal du serveur, on voit plusieurs **Access-Challenge** (les échanges du tunnel TLS et de MSCHAPv2) avant l'**Access-Accept** final.

</details>

### D3 – Le client vérifie-t-il le serveur ?

Jusqu'ici, le profil **ne contient aucune vérification** du certificat du serveur : le client a accepté **n'importe quel** certificat. Ajoute dans une copie `peap-ca.conf` la ligne qui désigne l'autorité de confiance. Ici, le certificat du serveur est **auto-signé** (installé avec le paquet `ssl-cert`) : il sert de sa propre autorité.

```text
  ca_cert="/etc/ssl/certs/ssl-cert-snakeoil.pem"
```

(à placer dans le bloc `network={ … }`). Relance : ______________________

Teste maintenant avec une **autre** autorité, qui n'est **pas** celle du serveur, dans une copie `peap-ca-autre.conf` :

```text
  ca_cert="/etc/ssl/certs/ca-certificates.crt"
```

Résultat : ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Avec le **bon** certificat de confiance : `SUCCESS`. Avec une **autre** autorité : **`FAILURE`** — le client **refuse le serveur**, car son certificat n'est pas signé par une autorité de confiance. C'est exactement la protection contre une **fausse borne** : sans cette ligne dans le profil, le client aurait envoyé ses identifiants à n'importe qui.

</details>
