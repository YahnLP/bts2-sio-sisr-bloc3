## Le laboratoire

Deux machines virtuelles **Debian** sur un réseau interne **isolé**, avec un compte `sudo` :

| Machine | Adresse | Rôle |
|---|---|---|
| `cible` | `10.40.0.20` | Petit site web **et** sonde Suricata, qui observe sa propre interface réseau |
| `attaque` | `10.40.0.10` | Génère le trafic du scénario (`curl`, `nmap`) |

> [!NOTE]
> Pour simplifier, la sonde est installée **sur la cible**. Dans une organisation, une sonde est une machine **dédiée**, branchée sur un port miroir : le principe est le même. Retrouve le nom de ton interface avec `ip -br a` (par exemple `enp0s3`) : il remplace `IFACE` plus bas.

**Contraintes.** **Instantané** des deux machines ; paquets : `suricata`, `jq` (sur `cible`), `curl` et `nmap` (sur `attaque`) ; tu **notes la sortie** de chaque commande (capture datée).

## Partie B – Installer et démarrer (≈ 30 min)

### B1 – La cible : un site, une sonde

Sur `cible` :

```bash
sudo apt install -y suricata jq python3
mkdir -p ~/web/catalogue && cd ~/web
echo "<h1>Cible du laboratoire</h1>" > index.html
echo "Catalogue" > catalogue/index.html
sudo python3 -m http.server 80 --bind 10.40.0.20 &
```

Sur `attaque` : `curl -s -o /dev/null -w "%{http_code}\n" http://10.40.0.20/` doit afficher `200`.

### B2 – Les règles

Sur `cible`, crée `~/local.rules` :

```text
# Regle 1 : outil d'attaque identifie par son User-Agent
alert http any any -> $HOME_NET any (msg:"LAB outil sqlmap (User-Agent)"; http.user_agent; content:"sqlmap"; nocase; classtype:web-application-attack; sid:1000001; rev:1;)
# Regle 2 : remontee de repertoire dans l'adresse demandee
alert http any any -> $HOME_NET any (msg:"LAB remontee de repertoire"; http.uri; content:"../"; classtype:web-application-attack; sid:1000002; rev:1;)
# Regle 3 : balayage de ports (beaucoup de SYN depuis la meme source)
alert tcp any any -> $HOME_NET any (msg:"LAB balayage de ports"; flags:S; threshold:type both, track by_src, count 20, seconds 5; classtype:attempted-recon; sid:1000003; rev:1;)
# Regle 4 (trop large, volontairement) : le mot select dans l'adresse
alert http any any -> $HOME_NET any (msg:"LAB injection SQL (large)"; http.uri; content:"select"; nocase; classtype:web-application-attack; sid:1000004; rev:1;)
```

> [!NOTE]
> La règle 2 contient **volontairement** une erreur (le tampon à chercher). Tu la trouveras en partie C.

### B3 – Vérifier, puis lancer

```bash
sudo mkdir -p /var/log/suricata-lab
sudo suricata -T -c /etc/suricata/suricata.yaml -S ~/local.rules \
  --set vars.address-groups.HOME_NET="[10.40.0.0/24]" -l /var/log/suricata-lab
```

`-T` **teste** la configuration sans la lancer ; `-S` charge **uniquement** ton fichier de règles ; `HOME_NET` désigne **ton** réseau.

Si le test réussit, lance la sonde **au premier plan** dans un **deuxième terminal** (arrêt par `Ctrl+C`) :

```bash
sudo suricata -c /etc/suricata/suricata.yaml -S ~/local.rules \
  --set vars.address-groups.HOME_NET="[10.40.0.0/24]" \
  --af-packet=IFACE -l /var/log/suricata-lab
```

Attends le message `Engine started`, puis **quelques secondes** de plus avant le premier test.

**Point de contrôle :** capture du test `-T` et du message `Engine started`.

## Partie C – Le scénario d'attaque (≈ 45 min)

Sur `attaque`, rejoue **dans cet ordre**, en notant l'heure de chaque ligne :

```bash
# 1. Outil d'attaque identifie
curl -s -o /dev/null -A "sqlmap/1.8" "http://10.40.0.20/index.html?id=1"
# 2. Remontee de repertoire
curl -s -o /dev/null --path-as-is "http://10.40.0.20/../../etc/passwd"
# 3. Requete LEGITIME qui contient le mot select
curl -s -o /dev/null "http://10.40.0.20/catalogue/?select=rouge"
# 4. Vraie injection
curl -s -o /dev/null "http://10.40.0.20/index.html?id=1%20UNION%20SELECT%20password"
# 5. Navigation normale
curl -s -o /dev/null -A "Mozilla/5.0" "http://10.40.0.20/"
# 6. Balayage de ports
nmap -sS -p 1-200 -T4 10.40.0.20
```

Sur `cible`, lis les alertes (attends quelques secondes) :

```bash
sudo cat /var/log/suricata-lab/fast.log
sudo jq -r 'select(.event_type=="alert") | [.alert.signature_id, .src_ip, (.http.url // "-")] | @tsv' /var/log/suricata-lab/eve.json
sudo jq -c 'select(.event_type=="http") | [.http.url, .http.status]' /var/log/suricata-lab/eve.json
```

**J'anticipe.** Avant de lire : pour chacune des six actions, la sonde alertera-t-elle ? ______________________

Complète le tableau :

| # | Action | Alerte ? (sid) | Vrai positif, faux positif, attaque manquée ou vrai négatif ? |
|---|---|---|---|
| 1 | Outil `sqlmap` | | |
| 2 | Remontée de répertoire | | |
| 3 | Requête légitime avec `select` | | |
| 4 | Injection `UNION SELECT` | | |
| 5 | Navigation normale | | |
| 6 | Balayage de ports | | |

**Je comprends.** Une des attaques n'a **pas** été signalée alors que la sonde la **voit** (la troisième commande de `jq` montre l'adresse demandée). Laquelle ? Compare l'adresse affichée par `jq` avec ce que cherche la règle : que remarques-tu ? ______________________

> [!NOTE]
> Indice : cherche, dans la documentation de Suricata, la différence entre les tampons `http.uri` et `http.uri.raw`.

## Partie D – Régler (≈ 55 min)

### D1 – Corriger la règle qui ne se déclenche pas

Dans `~/local.rules`, remplace `http.uri; content:"../";` par `http.uri.raw; content:"../";` dans la règle 2. Arrête la sonde (`Ctrl+C`), **relance-la**, rejoue **uniquement** l'action 2 et vérifie que l'alerte apparaît.

### D2 – Réduire le faux positif

La règle 4 déclenche sur l'action 3, légitime. Mets-la **en commentaire** (`#` au début de la ligne) et ajoute :

```text
# Regle 4 corrigee : "union" suivi de "select" (une vraie signature d'injection)
alert http any any -> $HOME_NET any (msg:"LAB injection SQL (UNION SELECT)"; http.uri; content:"union"; nocase; content:"select"; nocase; distance:0; classtype:web-application-attack; sid:1000005; rev:1;)
```

Relance, rejoue les actions 3 et 4.

**Je comprends.** Que signifie `distance:0` ? Pourquoi cette règle ne se déclenche-t-elle plus sur `?select=rouge` ? ______________________

### D3 – Une attaque que personne n'a prévue

Rejoue, depuis `attaque`, en **changeant l'outil déclaré** :

```bash
curl -s -o /dev/null -A "Mozilla/5.0" "http://10.40.0.20/index.html?id=1%27%20OR%20%271%27=%271"
curl -s -o /dev/null -A "Mozilla/5.0" "http://10.40.0.20/index.html?id=1/**/UnIoN/**/SeLeCt/**/1"
```

**J'anticipe.** Laquelle des deux lignes sera signalée ? ______________________

Puis constate. Pour celle qui est **manquée**, écris une **règle 6** (nouveau `sid`, par exemple 1000006) qui la détecte **sans** déclencher sur la navigation normale. Teste-la sur les actions 5 et 3.

**Je comprends.** Un attaquant qui change le `User-Agent` neutralise la règle 1. Que peut-on en déduire de la valeur d'une règle qui repose **uniquement** sur le nom d'un outil ? ______________________

### D4 – Une exception documentée

Imagine que l'équipe lance chaque nuit un **scanneur de vulnérabilités interne** (séance S13) depuis `10.40.0.10` : il déclencherait la règle 5 tous les soirs. Ajoute dans `/etc/suricata/threshold.config` (en `sudo`) :

```text
suppress gen_id 1, sig_id 1000005, track by_src, ip 10.40.0.10
```

Relance la sonde, rejoue l'action 4 : plus d'alerte pour la règle 5. **Mais** la règle 1 (outil `sqlmap`) continue de déclencher depuis cette adresse.

**Je comprends.** Remplis la **fiche d'exception** : règle, adresse, raison, responsable, date de revue. Que se passe-t-il si un attaquant prend le contrôle de `10.40.0.10` ? ______________________

> [!WARNING]
> Remets ensuite le fichier `/etc/suricata/threshold.config` dans son état initial (supprime la ligne ajoutée) pour ne pas fausser la suite du TP.

**Point de contrôle :** captures avant et après de chaque réglage.

## Partie E – Relier à la supervision (≈ 20 min)

```text
module(load="imfile")
input(type="imfile" File="/var/log/suricata-lab/fast.log" Tag="suricata" Severity="warning" Facility="local5")
```
