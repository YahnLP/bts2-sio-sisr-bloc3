   ______________________
3. Qu'est-ce que la **double extorsion** ?
   ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. **Disponibilité** (service rendu inaccessible par un rançongiciel), **intégrité** (fichier ou virement falsifié), **confidentialité** (fuite de données). On accepte aussi la **preuve**.

### A5 – Sauvegarde

13. Que dit la règle **3-2-1** ?
    ______________________
14. Quelle différence entre **RPO** et **RTO** ?
    ______________________
15. Pourquoi un **RAID** n'est-il pas une sauvegarde ?
    ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

13. **3** copies des données, sur **2** supports de nature différente, dont **1** hors site.
14. **RPO** : perte de données maximale acceptée (durée entre deux sauvegardes). **RTO** : durée maximale d'interruption acceptée avant la remise en service.

### A6 – RGPD

    ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

### A7 – Chiffrement

19. Quelle différence entre chiffrement **symétrique** et **asymétrique** ? Donne un avantage de chacun.
    ______________________
20. À quoi sert un **certificat** et qui le signe ?
    ______________________
21. Tu télécharges un fichier et son empreinte SHA-256 est identique à celle publiée par l'éditeur. Qu'est-ce que cela garantit, et que ne garantit-il pas ?
    ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

19. **Symétrique** : une seule clé, **rapide**, mais il faut la partager. **Asymétrique** : paire clé publique / clé privée, **pas de secret à partager** au préalable, mais plus lente.
20. Il **lie une identité à une clé publique** ; il est **signé par une autorité de certification** que le client juge de confiance.

</details>

### B1 – La configuration SSH réellement appliquée

**J'anticipe.** Le compte `root` peut-il se connecter directement en SSH ? L'authentification par mot de passe est-elle autorisée ? ______________________

```bash
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|maxauthtries|port) '
```

**Je comprends.** `sshd -T` affiche la configuration **réellement appliquée** (fichier principal et fichiers inclus), pas seulement ce qui est écrit dans un fichier.

Note les quatre valeurs : ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

### C1 – Durcir SSH

**J'anticipe.** Si on interdit la connexion directe de `root` et qu'on limite à 3 essais, qu'est-ce qui change pour un utilisateur normal ? ______________________

Crée un fichier de réglages dédié (les fichiers de `/etc/ssh/sshd_config.d/` sont lus avant le reste, et c'est la **première** valeur lue qui s'applique) :

```bash
printf 'PermitRootLogin no\nMaxAuthTries 3\n' | sudo tee /etc/ssh/sshd_config.d/50-durcissement.conf
sudo sshd -t && echo "configuration valide"
```

Recharge le service **seulement si le test affiche « configuration valide »** :

```bash
sudo systemctl reload ssh
sudo sshd -T | grep -Ei '^(permitrootlogin|maxauthtries) '
```

**Je comprends.** `sshd -t` **teste** la configuration sans l'appliquer : un fichier invalide rechargé peut empêcher toute connexion. Les sessions déjà ouvertes **ne sont pas coupées** par un rechargement.

Résultat de la dernière commande : ______________________

**Pour aller plus loin (facultatif).** Désactive l'authentification par mot de passe (`PasswordAuthentication no`) **uniquement après** avoir copié ta clé publique sur SRV (`ssh-copy-id`) et vérifié depuis CLI que la connexion par clé fonctionne dans une **nouvelle** session.

### C2 – Un pare-feu à politique restrictive

**J'anticipe.** Si la politique par défaut est « refuser », qu'est-ce qui doit être explicitement autorisé pour que SSH depuis CLI et le site web continuent de fonctionner ? ______________________

Crée le fichier de règles `/root/filtre.nft` avec l'éditeur de ton choix (`sudo nano /root/filtre.nft`) et le contenu suivant :

```text
#!/usr/sbin/nft -f
flush ruleset
table inet filtre {
  chain entrant {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    ct state invalid drop
    iif "lo" accept
    ip protocol icmp icmp type echo-request limit rate 5/second accept
    ip6 nexthdr icmpv6 accept
    ip saddr 192.168.50.0/24 tcp dport 22 accept
    tcp dport { 80, 443 } accept
  }
}
```

Vérifie la syntaxe **sans appliquer** :

```bash
sudo nft -c -f /root/filtre.nft && echo "syntaxe valide"
```

Applique-le, puis affiche les règles actives :

```bash
sudo nft -f /root/filtre.nft
sudo nft list ruleset
```

**Je comprends.** Chaque ligne a un rôle : le **suivi des connexions** (`established,related`) laisse passer les réponses aux connexions déjà autorisées ; l'interface locale (`lo`) reste ouverte ; le **ping** est limité en débit ; **SSH** n'est autorisé que depuis le réseau d'administration ; le web est ouvert à tous. **Tout le reste est refusé.**

**Retour arrière** si tu perds la main : dans la console, `sudo nft flush ruleset`.

Teste depuis **CLI**, puis note les résultats :

| Test depuis CLI | Résultat attendu | Résultat constaté |
|---|---|---|
| `ping -c 2 192.168.50.10` | répond | |
| `ssh utilisateur@192.168.50.10` | connexion | |
| `curl -I http://192.168.50.10` | réponse du serveur web s'il y en a un ; sinon « connexion refusée » | |
| `nc -zv -w 3 192.168.50.10 3306` | **pas de réponse** : le paquet est jeté | |

> [!NOTE]
> Le dernier test attend 3 secondes puis expire : c'est la différence entre `drop` (silence, la machine ne se signale pas) et `reject` (réponse « refusé »). Ces règles **ne survivent pas à un redémarrage** : pour les rendre permanentes, il faudrait les placer dans `/etc/nftables.conf` et activer le service `nftables`.

### C3 – Corriger un droit trop large

Un fichier de clients a été déposé avec des droits trop larges. Crée la situation, puis corrige-la :

```bash
sudo groupadd -f compta
sudo install -d -m 755 /srv/donnees
echo "client;montant" | sudo tee /srv/donnees/clients.csv > /dev/null
sudo chmod 666 /srv/donnees/clients.csv
stat -c '%a %U:%G %n' /srv/donnees/clients.csv
```

**J'anticipe.** Qui peut lire et modifier ce fichier avec `666` ? Quelle valeur et quel propriétaire faut-il lui donner pour que seule la comptabilité le lise ? ______________________

```bash
sudo chown root:compta /srv/donnees/clients.csv
sudo chmod 640 /srv/donnees/clients.csv
stat -c '%a %U:%G %n' /srv/donnees/clients.csv
```

**Je comprends.** `666` laisse **tout le monde lire et écrire** : un fichier de données personnelles accessible à tous est une atteinte à la **confidentialité** et une **violation potentielle** au sens du RGPD. Avec `640` et le groupe `compta`, seuls les membres du groupe lisent.
